# AurumPulse XAUUSD v6.49 — Implementation Plan

## Purpose
Translate the v6.49 architecture audit into a controlled implementation without modifying the v6.48 evidence baseline on `main`.

## Non-negotiable invariants
1. `main` v6.48 remains untouched until the new build passes compile and A/B testing.
2. No parameter optimization before execution-path instrumentation is verified.
3. No tick-loop indicator recalculation.
4. No trailing SL loosening.
5. No TP movement against the favorable direction.
6. Every pending order must have a reason code and lifecycle state in the journal.
7. Every broker modification must be deduplicated after price normalization.

## Execution pipeline

### BAR PATH — once per new closed bar
1. Read/cache Supertrend, Heiken Ashi, Entry Signal Pro, SuperSR and required MTF values.
2. Build a `MarketContext` snapshot.
3. Update trend state and detect fresh structure events.
4. Evaluate existing positions for dynamic TP/trailing targets using the cached context.
5. Evaluate pending-order state machine.
6. Evaluate market-entry state machine.
7. Reconcile/cancel stale pending orders.
8. Update dashboard at a controlled cadence.

### FAST PATH — every tick, minimal work
1. Refresh Bid/Ask.
2. For open positions only, evaluate emergency/profit-lock conditions that genuinely require intrabar prices.
3. Compare proposed SL with the currently installed SL after normalization.
4. Apply a broker-safe modify only when the price actually improves and the throttle permits it.
5. Do not call custom indicators, redraw dashboard objects, or recompute the full signal stack here.

## Entry state machine

`IDLE -> SETUP -> CONFIRMED -> EXECUTABLE`

A setup expires when its structural premise is invalidated.

### Market BUY/SELL
Requires a fresh momentum/structure event. A stale Supertrend flip is not sufficient. The market path is preferred only when price has not materially chased beyond the configured ATR/structure envelope.

### BUY LIMIT
Intent: buy a validated downside exhaustion / reversal zone.
Required evidence:
- downtrend or bearish extension;
- measurable exhaustion/extension;
- structural support or validated swing zone;
- rejection/reversal evidence;
- sufficient room to the invalidation level;
- no fresh bearish continuation event that invalidates the setup.

### SELL LIMIT
Mirror of BUY LIMIT for an uptrend exhaustion zone.

### BUY STOP
Intent: confirm an upward reversal/breakout after a downtrend.
Required evidence:
- prior bearish state;
- reversal structure;
- fresh bullish break/confirmation;
- stop price beyond the structure, respecting broker stop distance;
- cancellation if reversal evidence disappears before fill.

### SELL STOP
Mirror of BUY STOP for a downward reversal.

## Dynamic TP state machine

`INITIAL_TARGET -> EXTENDING -> FROZEN -> PROTECTED -> EXITED`

- Initial TP is derived from risk/ATR/structure.
- While trend quality remains strong, TP may extend only in the favorable direction.
- TP extension requires a new structural/momentum justification; it is not moved every tick.
- When trend quality degrades, freeze the TP and let smart trailing/profit protection control the exit.

## Smart trailing state machine

`UNPROTECTED -> BE_PROTECTED -> PROFIT_LOCK -> STRUCTURAL_TRAIL -> EMERGENCY_LOCK`

The transition depends on profit measured in ATR/R and current structure, not an arbitrary candle-count delay.

### Ratchet invariant
For BUY:
`newSL >= oldSL`

For SELL:
`newSL <= oldSL`

If the proposed value does not improve the protection after normalization, no `OrderModify` call is made.

## Performance controls

### Indicator cache key
`symbol + timeframe + closed-bar-time`

One indicator value set is calculated once per processing cycle and reused by all consumers.

### Dashboard cadence
Dashboard refresh is decoupled from the tick path. A state change or controlled timer/cadence may trigger redraw; ordinary price ticks must not redraw the complete panel.

### Broker modification gate
Before `OrderModify`:
- normalize price;
- compare against current SL/TP;
- verify broker stop/freeze distance;
- verify minimum improvement threshold;
- verify modify throttle;
- only then send modification.

## Required diagnostic counters

### Market
- setup created
- confirmed
- executable
- executed
- rejected: chase
- rejected: stale
- rejected: structure
- rejected: risk

### Pending
For each of BUY LIMIT, SELL LIMIT, BUY STOP, SELL STOP:
- candidate
- placement attempted
- placed
- placement failed + error
- filled
- expired
- cancelled by invalidation
- cancelled by opposite signal
- cancelled by risk gate

### Management
- TP extension count
- TP freeze count
- BE activation
- profit-lock activation
- structural trailing modification
- emergency intrabar lock
- skipped modify: unchanged
- skipped modify: throttle
- failed broker modify

## Test sequence

### Test A — compile/integrity
- compile v6.49;
- 0 errors;
- 0 warnings;
- verify required custom indicators are present.

### Test B — execution-path diagnostic
- same one-month period as the supplied baseline;
- same symbol/timeframe/spread assumptions;
- fixed conservative lot;
- collect all lifecycle counters.

### Test C — pending-order proof
Run controlled cases to prove each order type can be generated independently. Do not judge profitability yet.

### Test D — A/B performance
Compare v6.48 and v6.49 using identical tester settings. Record PF, net profit, DD, trades, average win/loss, and execution counts.

### Test E — stress/performance
Confirm that indicator cache and dashboard throttling eliminate repeated tick-level indicator work and visual flicker.

## Release gate
v6.49 must not replace v6.48 on `main` until the above evidence is reviewed and the new behavior is confirmed from the tester journal.
